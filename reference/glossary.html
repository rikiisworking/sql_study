Glossary

Shared terms for every lesson. Prefer these words when talking about queries.

Grain
What one row in a result (or table) represents. Example: “one row per order” vs “one row per order line.” Wrong grain is the root of many wrong totals.
Fan-out (join multiplication)
A join that matches one left row to many right rows, multiplying rows before later steps (especially SUM/COUNT). Results look “inflated,” not always empty or errored.
Predicate
A boolean condition in WHERE, JOIN … ON, or HAVING that filters or matches rows.
Sargable
A predicate the engine can use efficiently with an index or ordered/partitioned layout (e.g. col = ?, col >= ?). Wrapping the column in a function often kills this. See also predicate rewrite.
Partition pruning
Skipping entire partitions (folders / table partitions) that cannot match the query’s filters, so those files are never scanned. Needs filters the engine can map to partition columns.
Predicate pushdown
Applying a filter as close to storage as possible (file scan, Spectrum layer, data source) so less data is read into the engine’s main compute path.
Plan (query plan / execution plan)
The steps the engine chose: scans, joins, aggregates, shuffles. Inspected with EXPLAIN (wording varies by engine). See plan labels.
Index condition (access predicate)
A filter the engine can use to limit an index range or seek (e.g. PG Index Cond). Contrast a plain Filter applied after rows are already fetched.
Data redistribution (Redshift DS_*)
Moving rows across slices/nodes so a join or aggregate can complete. Labels like DS_DIST_NONE, DS_BCAST_INNER, DS_DIST_BOTH appear on Redshift join plans.
Scan
Reading many rows/blocks/files to find matches. Not always bad—but full scans on huge tables are the first place to look when something is slow.
Selectivity
How much a predicate shrinks the set. Highly selective filters (few rows match) are gold for performance when the engine can apply them early.
Shuffle (Spark / distributed)
Redistributing data across workers so a join or aggregation can complete. Often the expensive part of Spark SQL / Glue jobs.
Distribution key / distribution style (Redshift)
How rows are placed across nodes/slices. Styles: KEY (hash one column), ALL (full copy per node), EVEN (round-robin), AUTO (engine chooses). Same dist key on both sides of a frequent equijoin → collocated join, less redistrib. See lesson 0006 and four dist-style pictures.
Sort key (Redshift)
Physical row order on disk. Range/equality predicates can skip blocks via per-block min/max. Not the same lever as dist key (order vs placement). See lesson 0006.
Broadcast join
Copy a small side to every worker, then join locally. Spark: BroadcastHashJoin. Redshift analog: broadcast inner / DISTSTYLE ALL for small dims. Dangerous when the “small” side is not small.
Collocated join
Matching join keys already on the same slice/node so the engine need not redistribute for that join. Redshift signal: DS_DIST_NONE.
Skew (data skew)
Uneven work: one Redshift slice or one Spark shuffle partition/task holds far more rows or time than its siblings. Wall-clock follows the slowest worker. Not the same as an evenly large shuffle. See skew signals and lesson 0007.
Table skew
Stored rows piled on few Redshift slices. Check SVV_TABLE_INFO.skew_rows (max-slice rows ÷ min-slice rows). Official diagnostic query treats a ratio of 4.00 or higher as a reason to reconsider distribution style.
Query skew
This query’s work is uneven after filters/joins, even if the table looks even. Classic: DISTKEY on a date plus a narrow date range. Check SVL_QUERY_REPORT rows and elapsed time per slice.
AQE (Adaptive Query Execution)
Spark re-optimizes the plan while the query runs, using measured sizes instead of only the planner’s first guess. Default on since Spark 3.2 / Glue 4. Main tricks: coalesce tiny shuffle partitions, flip a sort-merge join to broadcast if a side turns out small, and split a skewed join partition. Flag: spark.sql.adaptive.enabled.
Richer join key
A join match with higher cardinality (more distinct values), so shuffle hashes spread. May be one high-cardinality column or a composite the question already requires. Not “add extra join columns for speed” — extra predicates change which rows match. See lesson 0007.
AQE skew join
The AQE feature that splits (and may replicate) fat sort-merge-join partitions into more even tasks. Needs spark.sql.adaptive.enabled and spark.sql.adaptive.skewJoin.enabled.
Three-valued logic (3VL)
SQL truth values: TRUE, FALSE, UNKNOWN. NULL comparisons yield UNKNOWN; WHERE keeps only TRUE.
Logical processing order
The order clauses are bound / conceptually applied when building a result — not the order you type them. Typical map: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → limit. Explains why SELECT aliases are invisible in WHERE.
HAVING
Filter on groups after GROUP BY. Can use aggregates. Contrast WHERE, which filters rows before grouping.
