0. The constraint: one DISTKEY on the fact

A fact table gets one distribution column. Only joins on that column can be collocated. Every other dim must move (or be ALL). 

          customers          products          stores
               \                 |                 /
                \                |                /
                 +------- fact.DISTKEY = ? ------+
                              only one

1. Collocate fact + one dim on the shared key

Put the dim’s primary key and the fact’s matching foreign key as DISTKEY. Same customer_id hashes to the same slice → join stays local.

Slice 0 order cust=2 order cust=2 cust 2
Slice 1 order cust=5 cust 5
Slice 2 order cust=8 order cust=8 cust 8

Join to products on product_id is not collocated. Those dim rows must be shipped (or the dim is ALL — rule 4).

Slice 0 order prod=9 need prod 9 →
Slice 1 prod 9 lives here
Slice 2 no prod 9

Which dim gets the one fact DISTKEY? The one you join most often, with the largest joining rows (next rule).

2. Pick the largest dim after the filter

This rule is about who spends the one DISTKEY, not “smaller leftover is better.” Moving 800 000 rows every night is expensive. Moving (or ALL-copying) 200 rows is cheap. So you collocate with the side that is still large after WHERE. The 200-row side is the easy one — do not spend DISTKEY on it. 

products table     50,000,000 rows
  WHERE active      →        200 rows   ← cheap to ALL / broadcast
customers table     2,000,000 rows
  WHERE region=east →    800,000 rows   ← expensive to move → DISTKEY here

Collocate fact + customers (the large filtered side).
ALL or broadcast the 200 products.

3. High cardinality in the filtered set

Many distinct values, still even after the usual predicates. Date as DISTKEY often looks even on the whole table, then “last 7 days” piles work on two slices.

Stored table (looks fine)

Slice 0JanMay
Slice 1FebJun
Slice 2MarJul
Slice 3AprAug

Same table, query = last week (only late Aug)

Slice 0Jan — skip
Slice 1Feb — skip
Slice 2Mar — skip
Slice 3Aug 11–17 (all of it)

That is query skew. Prefer a key that stays spread after the filter (often a customer / order id, not the date you always range).

4. ALL for dims that cannot share the fact key

Copy the whole (small) dim onto every node. Every slice can join locally. Cost: storage × nodes, slower loads.

Slice 0 fact… full dim copy
Slice 1 fact… full dim copy
Slice 2 fact… full dim copy

Use for small, slow-changing lookups you join many ways. Do not ALL a huge fact (lesson 0006 Q2).

How to read the official list as one decision

  1. Name the join you run most on the large leftover rows.
  2. DISTKEY fact FK + that dim PK on that column.
  3. Check: after typical filters, is the key still even? If not, pick another column.
  4. Other small dims: ALL (or Spark-style broadcast). Other large dims: accept redistrib, or a different table design.
