Lesson 0008 · Write the current row

One current row per key

Optimization (0004–0007) can wait on a live plan. Day-one write work: CDC snapshots, “latest status,” dedup. Same grain question as lesson 0001 — now the table already has many versions of one entity.

Mission: write production SQL that matches the question. The question here is “one row per customer, the newest version, every column of that version.” GROUP BY customer_id cannot do that: it collapses rows and will not let you pick status unless you also decide a rule for every other column.

Skill for this lesson

Write a window that numbers versions inside a key, then keep row_number = 1 — and name a tiebreaker so “latest” is one row, not a coin flip.

Window ≠ GROUP BY

PostgreSQL’s tutorial: a window calculates across related rows, but rows keep their identities. GROUP BY collapses; OVER annotates.

PostgreSQL — 3.5. Window Functions 

ROW_NUMBER() OVER (
  PARTITION BY customer_id          -- reset here = wanted grain
  ORDER BY updated_at DESC,
           event_id   DESC          -- who wins; make it unique
) AS rn

After this, you still have four rows. Numbers:

customer_idevent_idstatusrn
103closed1
102active2
101new3
204new1

Keep rn = 1 → customers 10 and 20, statuses closed and new. Omit PARTITION BY and the whole table is one partition: only event 3 survives.

Ties. Redshift: equal ORDER BY values get different row numbers, order nondeterministic. PostgreSQL says the same for row_number on peers. If two updates share a timestamp, add a unique column (here event_id) or you will pick a different “current” row on two runs.

Filter after the window (lesson 0003 again)

Windows run on the virtual table after WHERE / GROUP BY / HAVING. They are allowed in SELECT and ORDER BY, not in WHERE. To keep rn = 1, wrap: 

WITH ranked AS (
  SELECT
    customer_id, event_id, updated_at, status,
    ROW_NUMBER() OVER (
      PARTITION BY customer_id
      ORDER BY updated_at DESC, event_id DESC
    ) AS rn
  FROM events
)
SELECT customer_id, event_id, updated_at, status
FROM ranked
WHERE rn = 1;

Same shape in the PG tutorial (subquery, then WHERE pos < 3). Portable across Aurora (PG or MySQL 8), Redshift, Glue.

The MAX-join lookalike

SELECT e.*
FROM events e
JOIN (
  SELECT customer_id, MAX(updated_at) AS max_ts
  FROM events
  GROUP BY customer_id
) t
  ON  e.customer_id = t.customer_id
  AND e.updated_at  = t.max_ts;

Customer 10 still has two rows (active and closed). You asked for one current row; the join kept every row that shares the max timestamp — fan-out by tie. RANK() = 1 has the same hole. ROW_NUMBER always emits one 1 per partition.

QUALIFY — sugar, not the default

QUALIFY is HAVING for windows: filter after the window, no subquery. Markus Winand: not in today’s SQL standard; the portable form is the subquery above. 

SELECT customer_id, event_id, updated_at, status
FROM events
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY customer_id
  ORDER BY updated_at DESC, event_id DESC
) = 1;
