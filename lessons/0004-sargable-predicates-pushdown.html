Lesson 0004 · Optimization starts here

Predicates the engine can use

Correctness first (lessons 0001–0003). Now: filters that let engines skip work — indexes, sort keys, partitions, file scans — instead of reading everything and deciding later.

Mission: write and fix production SQL on Aurora / Redshift / Glue (Spark SQL). Slow queries often share one root: a predicate that looks right but is written so the engine cannot apply it early.

Skill for this lesson

Read a filter and say whether the column is “bare” enough for sargable use (index / sort / partition / pushdown). If not, rewrite it to a range or equality on the raw column — same meaning, less scan.

One idea, three labels

Same habit, different product words:

WordMeansWhere you hear it
Sargable Predicate can drive an index/ordered lookup Aurora-style / classic RDBMS
Partition pruning Skip whole partitions/folders that cannot match Spark / Glue, Redshift Spectrum, lakes
Predicate pushdown Apply filter close to storage (files, Spectrum layer) Spark, Spectrum, columnar formats

Mental model: bare column on the left, constants/ranges on the right (or the reverse, as long as you do not wrap the stored column in a black-box function).

The classic trap: function on the column

Markus Winand calls these obfuscated conditions: the WHERE is logically correct, but the engine cannot match it to an index (or ordered layout) on the base column. Functions are black boxes to the optimizer unless a matching function-based index exists. 

-- Same day? Looks fine. Often kills index / range use on sale_date.
WHERE YEAR(sale_date) = 2024
WHERE DATE(sale_date) = '2024-06-01'
WHERE TRUNC(sale_date) = DATE '2024-06-01'
WHERE TO_CHAR(sale_date, 'YYYY-MM') = '2024-06'

Preferred shape: explicit range on the bare column (works across engines; Winand’s portable fix for date periods): 

-- All of 2024
WHERE sale_date >= DATE '2024-01-01'
  AND sale_date <  DATE '2025-01-01'

-- One calendar day (if sale_date has a time component)
WHERE sale_date >= TIMESTAMP '2024-06-01 00:00:00'
  AND sale_date <  TIMESTAMP '2024-06-02 00:00:00'

Rule: transform the search term into bounds; leave the table column alone.

Source: Use The Index, Luke — Date Types (Markus Winand). “Write queries for continuous periods as explicit range condition.”

Other common obfuscations

  • WHERE amount + 0 = 100 / WHERE amount * 1 = … — math on column hides it
  • WHERE CAST(id AS text) = '42' — type mix; compare with correct type on the constant
  • WHERE first_name || last_name = ? — cannot use separate indexes on each name
  • WHERE LOWER(email) = LOWER(?) — needs expression index or store normalized form

Redshift states it plainly: avoid functions in query predicates; they raise cost by forcing more rows through intermediate steps. See Amazon Redshift — Best practices for designing queries.

Warehouse / lake: partitions and pushdown

On Glue/Spark and Redshift Spectrum, “index” is often partition columns + file layout (Hive-style …/year=2024/month=06/ or similar). 

-- Partition column is event_date (or year/month folders)
-- Helps pruning: filter matches partition metadata
WHERE event_date >= DATE '2024-06-01'
  AND event_date <  DATE '2024-07-01'

-- Hurts pruning: engine may not map YEAR(...) to partition keys
WHERE YEAR(event_date) = 2024 AND MONTH(event_date) = 6

Partition pruning skips whole partitions that cannot match. Predicate pushdown pushes remaining filters into the scan (e.g. Parquet row-group stats, Spectrum layer) so less data hits the cluster.

AWS: Pruning dynamic partitions (Spark on Glue/EMR) — apply filters early; confirm with EXPLAIN (PartitionFilters / DPP). Spectrum: Redshift Spectrum best practices — prefix partitions; filter on partition keys; check qualified vs total partitions.

Redshift local tables: sort keys echo the same habit

For tables on the cluster (not only Spectrum), Redshift recommends: restrict with WHERE so the planner can use row order (sort keys) and skip disk blocks; avoid functions on those columns. Put selective predicates early; filter both sides of a join when both tables can use their sort keys.

Same doc: designing queries best practices. Full sort/dist design is a later lesson; today only the predicate shape.

Check habit (15 seconds)

  1. Is the filtered column bare, or wrapped in a function / cast / math?
  2. Can I write the same meaning as = / >= / < / BETWEEN on the raw column?
  3. If the table is partitioned: does my filter mention the partition column in a form the catalog understands?
  4. After a rewrite, plan next (lesson 0005+): EXPLAIN — index range? partition filter? S3 scan size?
