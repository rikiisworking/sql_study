Lesson 0007 · Optimization

Slow join? Ask who is waiting

Lesson 0006 taught you that joins pay for movement. This lesson: movement can be even and large, or skewed — one slice or task owns the clock.

Mission: when a production join is slow, form a hypothesis (scan / join / shuffle / skew), then check evidence. A plan can show an Exchange or DS_DIST_*. Skew usually does not. It shows up at runtime, as one worker still running.

Skill for this lesson

Given a slow join, say whether the pain is even volume or skew, name the evidence, and pick the first lever — not “add workers and hope.”

One picture

Two different ways the same join can be slow. Each █ bar is one worker (Spark task, or Redshift slice) — not a column, and not “half the table.” Wall-clock is the last bar to finish. 

Shape A — even volume   ████ ████ ████ ████ ████ ████ ████ ████
  (everyone busy)

Shape B — skew (hog)    ██   ██   ██   ██   ██   ██   ██   ████████████████
  (one worker still going)

“Even” describes the split, not a second kind of data. Shape A can move a lot of bytes and still be even: eight fat bars. Shape B can move the same total bytes and finish later, because one join key (or one slice) ate a partition. Classic hot keys: one huge customer, a default 'UNKNOWN', or a pile of NULLs hashing together.

Those are examples of a fat key, not a rule to dropna / fillna before every join. Dropping or filling changes the answer (lessons 0001–0002) unless the question already excludes those rows. fillna('UNKNOWN') often creates the hog: many rows become one real join value. If unmatched/null keys are not part of the question, a deliberate WHERE key IS NOT NULL (or the equivalent filter) shrinks the shuffle with the same meaning. Speed fix after meaning is fixed: broadcast, AQE, or a richer key — not silent cleanup.

Spark / Glue: look at the stage, not the SQL

AWS’s Glue tuning guide: on the Spark UI Stage page, uneven Event Timeline bars, or Summary Metrics where Max duration / size dwarfs the median, mean data skew. Their example: median task ~13 s, max ~6.4 min on ~100× the data — that is a hog, not “Spark is just slow.”

AWS PG — Overcome data skew

First levers, in this order:

  1. Shrink, then broadcast (lesson 0006). Shrink = fewer rows (WHERE / filter) and fewer columns (SELECT only what the join needs — project). Same meaning, less to ship. If that side then fits in executor memory, broadcast it and you skip shuffling the hot key at all.
  2. AQE skew join. Adaptive Query Execution: Spark re-plans during the job from real sizes, not only the first guess. One of those mid-run tricks is splitting (and replicating if needed) a fat sort-merge partition into more even tasks. Needs spark.sql.adaptive.enabled and spark.sql.adaptive.skewJoin.enabled. Glue 4.0: AQE on by default; Glue 3.0: turn the flag on.
  3. Richer join key if the business allows it. Richer = the match column(s) have more distinct values, so hashes spread. That can be a different single column (high cardinality) or a composite the question already needs (ON a.id = b.id AND a.day = b.day). Extra predicates you do not mean will drop real matches — correctness first. Official Glue advice, not “add keys for luck.”

Spark — Optimizing Skew Join

Redshift: table skew vs query skew

Redshift states two goals for distribution:

  1. Even work — rows (and therefore join work) spread across slices.
  2. Less movement — matching join keys already on the same slice (collocated, often DS_DIST_NONE).

Those two can fight. Fact and dim both DISTKEY (customer_id) → matching rows already sit together → you win goal 2 (no redistrib for that join). If one customer is huge (“MegaCorp”), every MegaCorp fact row lives on one slice → you lose goal 1 (that slice is the hog). A collocated DISTKEY that is a hot key: less network, worse parallelism.

KindWhat is unevenWhere you look
Table skew Stored rows piled on few slices SVV_TABLE_INFO.skew_rows (max-slice rows ÷ min-slice rows). Diagnostic query: ratio ≥ 4.00 → reconsider dist style.
Query skew This query’s work, after filters SVL_QUERY_REPORT: same step, compare rows and elapsed_time across slices.

The date trap (official checklist, not folklore). DISTKEY on a date can look even on the whole table. Filter “last 7 days” and almost all surviving rows sit on a few slices — query workload is skewed. Pick a key that stays high-cardinality after common filters.

Day-job ladder

  1. See movement on the plan (0005 / 0006).
  2. Ask: did one task or slice own the clock?
  3. Spark: Stage max vs median. Redshift: skew_rows and/or slice report.
  4. Even and huge → shrink / layout / broadcast. Hog → do not just add nodes; fix the key or let AQE split the fat partition.
  5. One change → measure the same metric again.

Done when

  • You can separate “shuffle is big” from “one worker hog”
  • You name Spark UI max-vs-median, or Redshift skew_rows / slice report, as evidence
  • You try shrink→broadcast or a better key before adding cluster size
