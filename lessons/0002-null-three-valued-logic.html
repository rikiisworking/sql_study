Lesson 0002 · Correctness

NULL and three-valued logic

Production bug pattern #2: filters and NOT IN that look right but drop (or keep) rows because SQL is not true/false only.

After fan-out, the next silent wrong-result class is three-valued logic (3VL). Same engines you will touch (Spark SQL, Redshift, Aurora) all follow this model for core predicates.

Skill for this lesson

Read a predicate and say whether each comparison is TRUE, FALSE, or UNKNOWN — then remember: WHERE keeps only TRUE.

NULL is not a value

NULL means absent / unknown — “could be anything.” So most comparisons with NULL are not true or false; they are UNKNOWN.

ExpressionResult
NULL = 1UNKNOWN
NULL <> 1UNKNOWN
NULL = NULLUNKNOWN
NULL IS NULLTRUE
NULL IS NOT NULLFALSE

Never write col = NULL or col != NULL.

Write col IS NULL / col IS NOT NULL.

Source: Modern SQL — Three-Valued Logic (Markus Winand). Nothing equals null; not even null.

WHERE keeps only TRUE

For WHERE, HAVING, JOIN … ON, and CASE WHEN: the row (or branch) is taken only when the condition is TRUE. FALSE and UNKNOWN both fail the filter. 

-- Always empty: comparison to NULL is UNKNOWN for every row
SELECT *
FROM t
WHERE col = NULL;
-- Rows where col is missing
SELECT *
FROM t
WHERE col IS NULL;

AND / OR with UNKNOWN

Think: result is UNKNOWN only if it still depends on the unknown part.

ExpressionResultWhy
UNKNOWN OR TRUE TRUE OR already has a TRUE
UNKNOWN AND FALSE FALSE AND already has a FALSE
UNKNOWN OR FALSE UNKNOWN depends on the unknown side
UNKNOWN AND TRUE UNKNOWN depends on the unknown side
NOT UNKNOWN UNKNOWN negation of unknown is unknown

Production trap: NOT IN + NULL

Tiny tables:

orders.id
1
2
cancelled.order_id
2
NULL
 
-- "Orders that are not cancelled" — looks right, often wrong
SELECT o.id
FROM orders o
WHERE o.id NOT IN (SELECT c.order_id FROM cancelled c);

For o.id = 1: is 1 NOT IN (2, NULL) TRUE? No — because NULL could be 1. Result is UNKNOWN. WHERE drops the row. With a nullable column in the list, NOT IN is never TRUE for any outer value (it is either FALSE or UNKNOWN).

Fix: prefer NOT EXISTS (from lesson 1), or strip nulls from the list.

SELECT o.id
FROM orders o
WHERE NOT EXISTS (
  SELECT 1 FROM cancelled c
  WHERE c.order_id = o.id
);

Winand’s tip: don’t allow null in not in lists; use not exists for subqueries. EXISTS never returns UNKNOWN — only TRUE/FALSE.

Joins and NULL keys

Join condition a.key = b.key is UNKNOWN when either key is NULL → that pair does not match (same as “not TRUE”). Two NULL keys do not join to each other under =.

LEFT JOIN still keeps the left row; right-side columns become NULL when there is no match. Filtering those with WHERE right.id = … can accidentally turn an outer join into an inner join (predicate on right rejects UNKNOWN/NULL matches). Put right-table filters in ON when you mean “match only if …,” or use IS NULL when you mean “no match.”

Aggregates (quick map)

  • SUM/AVG/MIN/MAX ignore NULL inputs
  • COUNT(*) counts rows; COUNT(col) counts non-NULL col
  • SUM of no rows (or only NULLs) → NULL, not 0 — wrap with COALESCE(SUM(x), 0) if you need zero

Check habit (10 seconds)

  1. Any nullable column in this predicate?
  2. Did I write = NULL? → rewrite to IS NULL
  3. NOT IN (subquery)? → prefer NOT EXISTS if subquery can return NULL
  4. Filter on right side of LEFT JOIN? → confirm you still want outer-join semantics

Practice

Q1. What does this return?

SELECT * FROM t WHERE status = NULL;

Q2. NOT IN subquery that can return NULL?

Q4. Result of (NULL = 1) OR (1 = 1)?

Primary source (read ~15–20 min)

Modern SQL — The Three-Valued Logic of SQL (Markus Winand). Focus on: comparisons to null, WHERE keeps TRUE only, and the NOT IN (null, …) section.

Done when

  • You never write = NULL; you reach for IS NULL.
  • You treat NOT IN + nullable subquery as a smell → NOT EXISTS.
  • You can label a predicate TRUE / FALSE / UNKNOWN before running it.
