Lesson 0001 · Correctness first

Join fan-out: silent wrong totals

Production bug pattern #1: the query returns rows, the numbers look “almost right,” and SUM is quietly inflated because a join multiplied rows.

Mission link: you will write and fix production SQL on Redshift / Spark / Aurora. Slow queries matter. Wrong queries matter more. Fan-out is how correct-looking SQL lies.

Skill for this lesson

Before you trust a total, state the grain of every table in the join and check whether the join can fan out a row you planned to sum once.

True revenue of all orders: 100 + 50 = 150.

The trap

SELECT SUM(o.amount) AS revenue
FROM orders o
JOIN order_items i ON i.order_id = o.order_id;

What does the join produce before SUM?

order_idamountsku
1100A
1100B
250A

SUM(amount) = 100 + 100 + 50 = 250. No error. No empty set. Just a lie. Order 1’s amount was counted once per line item.

Rule: You may only SUM/COUNT a column at the grain it is defined at—unless you re-aggregate first.

Related: joins combine tables two at a time into intermediate results; wrong intermediate grain poisons later steps. See Markus Winand on the join operation. Redshift also warns against accidental cross-joins and uncontrolled cartesian products in query design best practices.

Three safe patterns

1. Aggregate the fine table first

SELECT SUM(o.amount) AS revenue
FROM orders o
JOIN (
  SELECT order_id
  FROM order_items
  GROUP BY order_id
) i ON i.order_id = o.order_id;

Here the join is 1:1 to orders that have items. Amount is still at order grain.

2. Don’t join if you only need “has items”

SELECT SUM(o.amount) AS revenue
FROM orders o
WHERE EXISTS (
  SELECT 1 FROM order_items i WHERE i.order_id = o.order_id
);

3. Sum at the grain you joined to

-- If the question is "total qty shipped", sum items, not order.amount
SELECT SUM(i.qty) AS units
FROM order_items i
JOIN orders o ON o.order_id = i.order_id
WHERE o.customer_id = 10;

Check habit (10 seconds)

  1. What is one row of each input table?
  2. After this join, what is one row?
  3. Am I aggregating a column defined at a coarser grain than the join result?

If (3) is yes → fan-out risk. Fix grain before tuning performance.
