Lesson 0006 · Optimization

Slow join? Ask how data moves

Lesson 0005 taught you to see movement in a plan (DS_*, Exchange, broadcast). This lesson: why it moves, and what you change first on Redshift vs Spark/Glue.

Mission: when a production join is slow, form a hypothesis (collocated vs redistributed vs broadcast vs shuffle/skew) before cargo-cult indexes. Layout and join strategy are the high-ROI levers on your stack.

Skill for this lesson

Given a fact↔dim (or large↔large) join, name: (1) whether the engine likely moves data, (2) which lever applies — Redshift dist/sort or Spark broadcast vs shuffle join, (3) what “good” looks like on a plan.

One mental model (both engines)

Distributed SQL pays for shipping rows across the network so matching join keys can meet on the same worker. Cheap join = keys already together (or one side small enough to copy everywhere). Expensive join = hash-redistribute both sides, or broadcast something huge.

SituationCheap pathPain signal
Big fact + small dim Copy dim to every node (broadcast / DIST ALL) Broadcast of a fat “dim”
Big fact + big dim, same join key often Collocate on that key (Redshift KEY; Spark pre-bucket/same partition) DS_DIST_BOTH / dual Exchange
Two huge tables, no small side Shuffle once, then hash or sort-merge Shuffle + skew (one partition huge)

Redshift: distribution places rows on slices

Every table has a distribution style. Default is often AUTO (Redshift may evolve ALL → KEY → EVEN as the table grows). You still need the model when EXPLAIN shows redistributes and when you design tables.

StyleWhere rows liveWhen
KEY Hash of one column → same value, same slice Frequent equijoins / group-bys on that column
ALL Full copy of the table on every node Small, rarely updated dimensions joined many ways
EVEN Round-robin across slices No clear join key; or pure scan/agg without joins
AUTO Redshift chooses / adjusts Default; still verify real plans under load

Collocated join: fact and one dimension both DISTKEY on the join column → matching rows already on the same slice → plan often shows DS_DIST_NONE (lesson 0005). Fact table gets one dist key — pick the dimension you join most (and whose filtered size is large).

Skew trap. Low-cardinality or seasonal keys (e.g. “all sales on one holiday date as DISTKEY”) pile work on few slices. Prefer high-cardinality keys that stay even after common filters.

Official checklist: Choose the best distribution style · pictures: four dist-style pictures; styles defined in Distribution styles.

Redshift: sort key = order on disk

Rows are stored sorted by the sort key. The optimizer uses min/max per block to skip blocks outside a range — same “don’t read what you don’t need” idea as sargable predicates (0004).

  • Query mostly “recent window”? Leading sort column = timestamp/date.
  • Heavy equality/range on one column? That column as sort key.
  • Join often on the same column you dist on? Sort + dist on that join key can enable merge join without re-sort.
  • AUTO sort is fine until plans or slow range filters say otherwise.

Choose the best sort key

Spark / Glue: join strategy = how keys meet

Spark does not have Redshift DISTKEY on every warehouse table, but the physics match: either broadcast a small side, or shuffle so keys co-locate, then join.

StrategyIdeaPlan smell
Broadcast hash Small side copied to all executors; no big shuffle of the fact BroadcastHashJoin, BroadcastExchange
Sort-merge Shuffle both sides by key, sort, merge (common for large↔large) SortMergeJoin + Exchange hashpartitioning
Shuffle hash Shuffle both; build local hash on smaller side per partition ShuffledHashJoin (when chosen)

Default auto-broadcast threshold is small (docs cite spark.sql.autoBroadcastJoinThreshold, often 10 MB). A “small” dimension that is actually 500 MB will not broadcast unless you filter/project it first or hint deliberately. Hints (Spark 3+): /*+ BROADCAST(t) */, MERGE, SHUFFLE_HASH, … Prefer shrink-the-side (select needed columns, filter early) before forcing broadcast of a monster.

AWS PG — Using join hints in Spark SQL; Spark SQL performance tuning (AQE can flip sort-merge → broadcast when runtime stats allow).

Transfer map (day-job)

  1. See movement on plan (0005): DS_* or Exchange / join type.
  2. Redshift: can dist/sort make this join collocated or block-skip? If not your table, note layout for the owner.
  3. Spark/Glue: can one side fit broadcast after filter/project? Else expect shuffle; watch skew on join key.
  4. Change one lever → EXPLAIN again → compare movement, not vibes.
