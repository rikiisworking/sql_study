Lesson 0003 · Reading complex SQL

Logical processing order

You write SELECT first. The engine does not think that way. Wrong mental order → “invalid column” errors, bad filters, and misread production queries.

Mission: read and fix multi-clause SQL on Redshift / Spark / Aurora. This lesson is the map for any engine’s SELECT. Builds on fan-out (join before aggregate) and 3VL (when filters apply).

Skill for this lesson

Trace a query in logical order and predict: which names exist at each step, what grain the rows have, and whether a filter is row-level or group-level.

Written order ≠ logical order

How people type a query:

SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY …

How SQL logically builds the result (binding / processing order):

  1. FROM / JOIN / ON — build the working row set
  2. WHERE — keep rows where predicate is TRUE
  3. GROUP BY — collapse to groups
  4. HAVING — keep groups where predicate is TRUE
  5. SELECT — compute output expressions / aliases
  6. DISTINCT — drop duplicate output rows
  7. ORDER BY — sort
  8. Limit / TOP / OFFSET … FETCH / engine LIMIT

Microsoft documents this as the logical processing (binding) order of SELECT: FROM → ON → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → TOP.

Primary source: SELECT (Transact-SQL) — Logical processing order. Physical plans may reorder work for speed; the result must match this logic.

Why this bites in production

1. SELECT aliases do not exist in WHERE

-- Error (or wrong engine): revenue not defined yet
SELECT amount * qty AS revenue
FROM order_items
WHERE revenue > 100;

WHERE runs before SELECT. Alias revenue is not born yet. 

-- Repeat expression, or filter later
SELECT amount * qty AS revenue
FROM order_items
WHERE amount * qty > 100;

-- Or wrap
SELECT *
FROM (
  SELECT amount * qty AS revenue
  FROM order_items
) x
WHERE revenue > 100;

Many engines allow the alias in ORDER BY (and sometimes GROUP BY / HAVING) because those steps are at or after SELECT. Do not assume every dialect is the same — when unsure, repeat the expression or use a subquery/CTE.

2. WHERE filters rows; HAVING filters groups

SELECT customer_id, SUM(amount) AS total
FROM orders
WHERE status = 'paid'          -- row filter (before group)
GROUP BY customer_id
HAVING SUM(amount) > 1000;     -- group filter (after group)
ClauseSeesCan use aggregates?
WHERE Individual rows after join No (SUM not computed yet)
HAVING Groups Yes

Put non-aggregate filters in WHERE when possible (smaller set before grouping). Use HAVING for conditions on the aggregate result.

3. JOIN (and fan-out) happen before WHERE and aggregates

From lesson 1: the join builds an intermediate set first. Then WHERE, then GROUP BY/SUM. That is why inflated join rows poison totals — multiplication is step 1 of the map.

4. LEFT JOIN + WHERE on the right table

SELECT o.id, i.sku
FROM orders o
LEFT JOIN order_items i ON i.order_id = o.order_id
WHERE i.sku = 'A';

Logically: outer join produces rows (with NULL right sides), then WHERE i.sku = 'A' rejects NULL right sides (lesson 2: UNKNOWN fails WHERE). Effect often becomes an inner join. If you meant “only match item A, keep orders without it,” put the item filter in ON: 

LEFT JOIN order_items i
  ON i.order_id = o.order_id
 AND i.sku = 'A'

Walk one query (grain at each step)

SELECT o.customer_id,
       COUNT(*) AS paid_orders
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'paid'
GROUP BY o.customer_id
HAVING COUNT(*) >= 2
ORDER BY paid_orders DESC;
  1. FROM/JOIN — grain: one row per (order, matching customer)
  2. WHERE — drop non-paid orders
  3. GROUP BY — grain: one row per customer
  4. HAVING — drop customers with fewer than 2 paid orders
  5. SELECT — shape columns; alias paid_orders appears
  6. ORDER BY — sort (alias OK on most engines)

CTEs fit the same map

WITH paid AS (
  SELECT customer_id, amount
  FROM orders
  WHERE status = 'paid'
)
SELECT customer_id, SUM(amount) AS total
FROM paid
GROUP BY customer_id;

Each CTE is its own logical SELECT. Outer query only sees the CTE’s result columns. Use CTEs to name intermediate grain (lesson 1 fix patterns).

Check habit (10 seconds)

  1. Walk the query: join → where → group → having → select → order
  2. At each step: what is one row?
  3. Alias used before SELECT? → illegal or dialect luck — rewrite
  4. Aggregate in WHERE? → move to HAVING or subquery
  5. Filter on right of LEFT JOIN in WHERE? → confirm intent
