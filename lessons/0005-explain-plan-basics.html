Lesson 0005 · Optimization

Read a plan before you guess

You rewrote a predicate (lesson 0004). Did the engine care? EXPLAIN is how you check — same mission skill on Aurora, Redshift, and Spark/Glue, different labels.

Mission: fix production SQL under real volume. Hypothesis first (scan / join / shuffle / skew), then evidence from a plan or metrics — not cargo-cult indexes. This lesson is the vocabulary for that evidence.

Skill for this lesson

Given a plan tree, answer four questions: (1) where do rows enter (scan)? (2) what filters run at the scan vs later? (3) how do tables meet (join type)? (4) what might be expensive (full scan, broadcast, shuffle)?

How to read any plan

  1. Tree, not a list. Indentation = parent/child. Data flows from leaves up (or “read bottom → top” on Redshift-style text).
  2. Leaves = scans. Table/file access lives here: sequential scan, index scan, FileScan parquet, Spectrum S3 scan.
  3. Nodes above = work. Filter, join, aggregate, sort, exchange/shuffle, network to leader.
  4. Costs are relative. Planner units, not wall-clock. Use them to compare steps inside one plan; confirm with actuals when available.

PostgreSQL documents this tree model and the cost/rows/width fields clearly — best map for Aurora PostgreSQL and a clean mental model for other engines. PostgreSQL — Using EXPLAIN.

PostgreSQL-shaped plan (Aurora PG / teaching map)

EXPLAIN SELECT * FROM tenk1 WHERE unique1 < 100;

 Bitmap Heap Scan on tenk1  (cost=5.06..224.98 rows=100 width=244)
   Recheck Cond: (unique1 < 100)
   ->  Bitmap Index Scan on tenk1_unique1  (cost=0.00..5.04 rows=100 width=0)
         Index Cond: (unique1 < 100)
FieldMeaning
cost=a..bStartup cost .. total cost if node runs to completion (arbitrary units)
rows=Estimated rows emitted by the node (not always rows scanned)
width=Estimated average row size (bytes)
Index CondUsed to seek/limit index range (good sign for sargable filter)
FilterApplied after rows are fetched — still pays for those rows

Index Cond vs Filter is lesson 0004 made visible: bare unique1 < 100 can be an index condition; a function on the column often becomes only a filter (or forces a seq scan).

EXPLAIN ANALYZE (PG) runs the query and adds actual times/rows. Use on read-only probes; wrap writes in a transaction you roll back. Side effects still happen unless you prevent them.

Redshift: same idea, XN + data movement

explain select eventname, count(*) from event group by eventname;

XN HashAggregate  (cost=131.97..133.41 rows=576 width=17)
  ->  XN Seq Scan on event  (cost=0.00..87.98 rows=8798 width=17)

Read bottom → top. Redshift cost/rows/width play the same relative role. Official note: EXPLAIN does not run the query; it is a simplified view (parallel detail lives in SVL views after a real run).

Join plans add how data moves — critical on a cluster:

LabelMeans (roughly)
XN Seq ScanTable scan (every row/block path considered)

DS_DIST_NONENo redistribute — collocated join (good)
DS_BCAST_INNERBroadcast inner table to all nodes
DS_DIST_INNER / BOTHRedistribute for the join (network cost)

Spark / Glue: FileScan and filters

In Spark SQL, default EXPLAIN shows a physical plan. Start at the bottom: scan nodes, then joins, aggregates, exchanges.

  • FileScan parquet … PartitionFilters: […] — partition pruning in play
  • PushedFilters: […] — predicate pushdown into the data source
  • Exchange / shuffle — data movement across executors (often the pain)
  • BroadcastHashJoin vs SortMergeJoin — small side broadcast vs sort-merge after shuffle

Spark SQL — EXPLAIN; earlier lesson’s DPP note: dynamic partition pruning (look for PartitionFilters / dynamicpruningexpression in EXPLAIN).

Portable 60-second checklist

  1. Find each scan. Full table/file scan on a huge relation? Why?
  2. Is your selective filter an access/index/partition condition, or only a late filter?
  3. Join: nested loop on big inputs? Unexpected broadcast? Spark Exchange explosion?
  4. Row estimates absurd (1 vs millions)? Stats stale — ANALYZE / table stats matter.
  5. Change one thing (predicate rewrite from 0004, or join key) → EXPLAIN again → compare.

Aurora dialect still open. If Aurora is PostgreSQL-compatible, PG docs map almost 1:1. If MySQL-compatible, plan text differs (EXPLAIN / EXPLAIN ANALYZE formats) but the same four questions apply. Tell the agent when you know which.
