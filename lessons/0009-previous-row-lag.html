Lesson 0009 · Write the previous row

What was this key last time?

Lesson 0008 keeps one current version. Day-job next: “did status flip?”, “qty vs last event.” Same window machinery — look backward one row, keep every row.

Mission: write SQL that matches the question. The question here is “for each event, attach that customer’s previous status, then name who flipped.”

Skill for this lesson

Write LAG with the same PARTITION BY grain as 0008, but ORDER BY forward in time plus a unique tiebreaker — then treat the first row’s NULL as “no previous,” not as a value (lesson 0002).

LAG looks one row back

PostgreSQL: lag(value [, offset [, default]]) returns value from the row offset rows before the current row in the partition. Omit extras → offset 1, default NULL.

PostgreSQL — 9.22. Window Functions · Redshift — LAG · Spark — Window Functions 

LAG(status) OVER (
  PARTITION BY customer_id          -- reset here = same grain as 0008
  ORDER BY updated_at ASC,
           event_id   ASC           -- earlier wins; make it unique
) AS prev_status

After this you still have four rows (window ≠ GROUP BY):

101newNULL
102activenew

Redshift’s own example: the first purchase in the ordered partition has no earlier row, so LAG is null there.

Direction. 0008 used ORDER BY … DESC so rn = 1 is newest. LAG means “the row before me in this order.” For “previous in time,” sort ascending (oldest first), same unique tiebreaker. Flip the sort and you attach the next event instead — that is LEAD.

Name the flip — watch the first-row NULL

WITH lined AS (
  SELECT
    customer_id, event_id, updated_at, status,
    LAG(status) OVER (
      PARTITION BY customer_id
      ORDER BY updated_at ASC, event_id ASC
    ) AS prev_status
  FROM events
)
SELECT customer_id, event_id, prev_status, status
FROM lined
WHERE prev_status IS NOT NULL
  AND status <> prev_status;

Result: event 2 (new → active) and event 3 (active → closed). Customer 20 never had a previous row.

WHERE status <> prev_status without the IS NOT NULL test fails 3VL: 'new' <> NULL is UNKNOWN, and WHERE keeps only TRUE — first rows vanish and you might think that is the flip filter working. It is not. You dropped “no previous.”

Same 3VL rule as lesson 0002 / Modern SQL — Three-Valued Logic.

Do not self-join to “max earlier timestamp”

SELECT e.*, p.status AS prev_status
FROM events e
LEFT JOIN events p
  ON  p.customer_id = e.customer_id
  AND p.updated_at  = (
        SELECT MAX(x.updated_at)
        FROM events x
        WHERE x.customer_id = e.customer_id
          AND x.updated_at  < e.updated_at
      );

Events 2 and 3 share a date, so event 3’s “max earlier date” is 2024-01-01 — it skips event 2. Same-day ties pick the wrong neighbor (or fan out if two rows share that max). LAG plus a unique ORDER BY does not have that hole.

Not a frame lesson. Redshift: LAG’s OVER must not contain a ROWS / RANGE frame. Running SUM() OVER (ORDER BY …) does use the default frame (start of partition through current peers) — that is a later skill, only if the day job needs it.
